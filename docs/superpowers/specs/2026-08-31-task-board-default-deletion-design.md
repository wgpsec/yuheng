# 任务看板删除设计

状态：已按 TDD 实施，待最终审计

目标版本：`0.4.x`

## 1. 背景

当前任务模块把 `default` 看板硬编码为不可删除。随着用户创建多个真实看板，这会留下无法清理的空看板，也无法表达用户希望将另一看板作为默认入口的意图。删除看板还必须避免丢失其中的任务和自定义列。

## 2. 目标

- 允许删除当前默认看板；确认后看板内的任务类型和任务全部级联删除。
- 删除默认看板后，由删除后按位置最早的剩余看板接替默认入口；后续省略 `boardId` 的任务 API 使用该看板。
- 删除看板、级联数据、默认看板更新和位置整理在同一个 SQLite 事务中完成，任一步失败都回滚。
- 不新增数据库表、业务字段、持久化状态机或新 endpoint；默认看板 ID 复用 `app_settings` 的 `default_task_board_id`。

## 3. 不变边界

- 不改变任务、任务类型和看板的现有数据结构。
- 删除不迁移、不复制任务，也不重建任务 ID；任务及其类型随看板一并删除。
- 不影响看板重命名、排序、单任务跨看板移动或备份格式。
- 旧数据库没有默认设置时继续使用 `default`（若该看板存在）；读取到失效设置时回退到当前最早看板，并保持可用。

## 4. 公开行为

### 4.1 删除调用

`deleteTaskBoard(boardId, legacyReplacementBoardId?)` 要求：

1. `boardId` 为非空字符串；第二个参数仅为旧版本调用兼容参数，不参与删除行为。
2. 源看板存在。
3. 数据库至少保留一个看板；删除最后一个看板失败。

删除普通或默认看板都遵循同一规则。默认看板常量只用于旧数据兼容，不再作为不可删除的业务限制。

### 4.2 级联删除

- 事务内先删除源看板下的任务，再删除任务类型，最后删除看板。
- 任务删除触发现有搜索索引等关联清理；任何失败都会回滚整个删除操作。

### 4.3 默认看板解析

- `app_settings` 以 `default_task_board_id` 保存当前默认 ID。
- 删除操作在同一事务内将该设置写为删除后按位置最早的剩余看板 ID。
- 所有省略 `boardId` 的 Store/Repository 任务读写入口动态解析该设置；显式传入的 ID 行为不变。
- 应用启动或设置失效时，回退到 `default`，再回退到按位置最早的看板；不创建额外看板。

## 5. IPC 与前端

- 保持 `tasks:boards:delete` endpoint 不变；preload 和 Desktop Bridge 可继续接受旧的第二参数，但生产调用只传 `boardId`。
- Sidebar 删除任意看板都打开统一确认交互，明确提示看板内全部任务和任务类型将永久删除；仅剩一个看板时仍不能删除。
- 删除成功后刷新看板列表，并切换到新的默认看板；后端错误显示在现有看板错误区域。
- 不在确认前执行删除，不用浏览器端过滤代替后端事务。

## 6. TDD 验收矩阵

| 行为 | 验收 |
| --- | --- |
| 普通看板删除 | 看板内任务类型和任务全部删除 |
| 默认看板删除 | 剩余看板成为默认看板，省略 `boardId` 的创建/列表使用该看板 |
| 级联清理 | 删除任务后，搜索索引等现有关联数据同步清理 |
| 删除最后看板 | 失败且所有数据不变 |
| 删除空看板 | 无需迁移目标即可删除；删除默认空看板后剩余看板成为默认 |
| 事务失败 | 源看板、任务、默认设置均保持删除前状态 |
| 重启 | 默认看板设置持久化，重新打开 Store 后行为一致 |
| IPC/前端 | 确认后直接删除全部内容；删除成功后视图切换 |
